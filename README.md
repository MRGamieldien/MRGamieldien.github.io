## SAEON Project Portfolio

### Project Overview

The **SAEON Real-Time Rainfall Monitoring System** is a team project aimed at giving researchers easier access to environmental observations from remote sites. My recorded role is **Project Leader and hardware integration lead**, with responsibilities covering requirements, hardware coordination and acceptance decisions.

The project documents specify an **ESP32 WROOM-32** and **TR-525M rain gauge**, with **DHT11 used for testing** and **SHT31 selected for the final temperature and humidity measurements**. **Firebase** is the database platform.

The planned remote data route connects the ESP32, SIM7000G cellular module, HiveMQ Cloud MQTT, a backend ingestion service, Firebase and the dashboard.

The photographs and videos below document laboratory prototypes and practical tests. Some show earlier sensor experiments and a different development board. They show the development process; final SHT31 verification, installation and field acceptance remain open in the project records.

### User Stories and Tasks

📄 [View the User Stories and Tasks](SAEON%20documents%20and%20evidence/SAEON_User_Stories_and_Tasks.pdf)

**About the document**

This document contains 13 user stories covering rainfall, temperature and humidity, remote transmission, Firebase storage, dashboard views, exports, station health, secure access, responsive layouts, power, deployment and maintenance.

Each story explains a user's need and breaks it into acceptance criteria and practical tasks, with links to the product backlog.

**My reflection**

The user stories helped me connect the electronics to the researcher's needs. For example, measuring rainfall involves more than displaying a number: the system must count tips correctly, avoid duplicate counts and convert the result into the right unit.

Breaking that requirement into tasks made the work easier to understand and test. I also learned why acceptance criteria should identify the sensor being tested. A DHT11 reading supports prototype development, while SHT31 performance still needs its own evidence.

In future, I would agree the expected result and test method before starting each task so that success is easier to demonstrate.

### Sprint Backlog

📄 [View the Sprint Backlog](SAEON%20documents%20and%20evidence/SAEON_Sprint_Backlog.pdf)

**About the document**

The sprint backlog turns the wider product work into 13 weekly plans. Each sprint includes a goal, selected tasks, task leads, proposed effort, acceptance criteria and evidence requirements. It also identifies work that must carry forward.

The effort figures are proposed estimates, rather than verified historical hours, and the 48-hour field-test duration is distinguished from the active time needed to run it.

**My reflection**

This document clarified the difference between a product backlog and a sprint backlog. The product backlog shows the wider work, while the sprint backlog explains what a particular week is intended to achieve and who will lead each task.

Seeing hardware setup, sensor testing and later integration separated into smaller goals made dependencies easier to recognise. I also learned that a planned date does not prove that work finished on that date.

In future, I would compare estimates with actual effort and record review decisions at the end of each sprint, especially when unfinished work needs to move forward.
